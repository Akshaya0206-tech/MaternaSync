# MaternaSync

React/TypeScript patient, doctor and caregiver (a relative or friend the woman invites) portals backed by FastAPI and SQLite, with a care assistant that does routine administrative work for the doctor. The care-team portal is switched off at sign-in but kept in the code (see Care-team login below). The roadmap implementation reuses the existing episodes, assignments, consultations, documents, questions, tasks, notifications, journeys and audit logs.

## Run locally (PowerShell)

```powershell
npm.cmd install
python -m venv backend/venv
backend/venv/Scripts/python.exe -m pip install -r backend/requirements.txt
backend/venv/Scripts/python.exe backend/fetch_reference_documents.py
backend/venv/Scripts/python.exe -m uvicorn backend.app.main:app --reload --port 8001
```

`fetch_reference_documents.py` is optional: it downloads the open-licence guideline PDFs for passage search (see Reference Library below). In another terminal, run `npm.cmd run dev`, then open `http://localhost:5173/signin`. Existing installations can retain their virtual environment and database. New tables are additive and created at API startup. Demo seeds are idempotent.

## Deploying

The website goes on Vercel and the API on a host that keeps a process running (Render blueprint included). Steps, settings, a troubleshooting table and what was and was not tested are in [DEPLOYMENT.md](DEPLOYMENT.md). Two settings connect them: `VITE_API_BASE_URL` (on the website, at build time) and `MATERNASYNC_CORS_ORIGINS` (on the API).

### Care-team login

The care-team login is **switched off** and replaced by the care assistant plus the doctor. Nothing was deleted: every care-team page, route, endpoint and test is still in the code. Signing in as care team (or using an old care-team token) is refused with a plain message by one check, `deps.refuse_sign_in`, and the nurse, coordinator and "other" sign-up roles are hidden and refused. Set `MATERNASYNC_CARE_TEAM_ENABLED=true` and restart to bring it all back; the automatic care-team tasks and notifications for new uploads and questions come back with it.

### Governance and integrations

Starter education modules are seeded in all four languages as drafts. A doctor approves them from Clinical Settings, one at a time or as a batch with an explicit "I reviewed each" confirmation, before the care companion or summaries can use them. The Hindi, Tamil and Telugu wording of the app and of the starter modules should be checked by a native speaker from the clinic before real use. `node tests/i18n-coverage.mjs` fails if any patient-portal string lacks a translation, and `node tests/patient-references.mjs` checks that every References topic is complete in all four languages.

Follow-up flags and the ICD-10 lookup are deterministic lookups into lists a doctor approved. Follow-up flags only concern check-ins and tasks. The ICD-10 lookup answers what the doctor types and does not read the note; the doctor ticks any code. None of this is a clinical score, a diagnosis or treatment advice, and nothing is acted on until a doctor decides. Clinical resources start as **DRAFT**; approval records the acting doctor and requires a future review date. This is a single-clinic prototype governance workflow, not a claim of institutional or regulatory approval.

**Reference Library.** Real documents only. The earlier demonstration guidelines and the one-link-per-publisher placeholders are removed at startup (an approved placeholder is retired, not deleted, so its history stays in the audit log). The entries live in `backend/app/data/reference_library_*.json` and are loaded idempotently. It is a personal, unversioned shelf: references that came with the app are the same for every doctor and read-only; anything a doctor adds, and every private note, is visible to that doctor only. Licences differ, so only openly licensed documents (WHO under CC BY-NC-SA 3.0 IGO; the MoHFW GDM guideline, which allows excerpts with acknowledgement; and four FIGO papers that are open access under CC BY or CC BY-NC, the licence confirmed on Europe PMC) have their PDFs kept for passage search; ICMR, NICE (outside the UK), SIGN, RCOG, ACOG, SMFM, RANZCOG and the other societies are link-only. Run `backend/venv/Scripts/python.exe backend/fetch_reference_documents.py` once to download those 19 PDFs from their publishers into `backend/reference_documents/` (ignored by git; Europe PMC turns scripts away, so if the four FIGO files report HTTP 403, open each link in a browser and save the PDF under the name the script prints); the next API start splits them into searchable passages. A few entries say in their edition note that they may have been superseded, and figo.org blocks automated checks, so check the current edition before relying on one. A doctor's own PDFs (up to 25 MB, 400 pages) are searched too. The lists that other parts of the app read from (follow-up rules, ICD-10 code sets, patient education, care pathways and note layouts) live under **Clinical Settings**, where each still needs a doctor's approval.

**Searching by meaning (optional).** A doctor can type a question in Hindi, Tamil or Telugu and still reach the English passage. A small multilingual model (multilingual-e5-small, MIT licence, run on this server with onnxruntime) gives every passage and every reference a vector, and a question is matched to the closest ones; the result is merged with the word search by rank. It ranks and nothing else: every hit is still the document's own sentence with its page, nothing is written, translated or summarised, and a hit found only by meaning carries a **Found by meaning** label. Passages are about a short paragraph (around 700 characters, never across a page): the PDF reader used to give one passage per layout block, 16,316 of them with a median of 139 characters ("for the woman and baby."), and they are now joined in reading order into about 5,700 (median 718 characters). Words the reader had mistaken for a heading are put back where they were, and invisible soft hyphens are removed. That helps the word search too (which now needs 70% of a question's words in a passage instead of half, because a passage is longer than a fragment), and it happens by itself the first time the API starts. Reference lists, licence pages and journal headers (about 10% of the passages) are kept out of the results of both searches: they are full of the subject's words, because every paper they cite is about it, and they would outrank real paragraphs. To switch the meaning search on, from `backend/`: `python fetch_search_model.py` (135 MB, checksums verified), `python build_semantic_index.py` (about 2 to 3 minutes, writes an 11 MB index; run it again after attaching a PDF), then restart the API. No new package is needed: onnxruntime, tokenizers and numpy already come with the speech library. `python evaluate_semantic_search.py` measures it on 18 topics asked in English, Hindi, Tamil and Telugu, plus 13 questions that have no answer in the library (the Hindi, Tamil and Telugu wordings were written for the check and have not been reviewed by a native speaker). A right reference was among the first 5 for 17 of 72 questions with words alone and 54 of 72 with meaning added (English 17 → 18, Hindi 0 → 16, Tamil 0 → 11, Telugu 0 → 9, of 18 each); a passage that came from a right document and also said the topic's own words was among the first 8 for 8 of 36 and 22 of 36 (Hindi 5, Tamil 3, Telugu 5 of 9); the questions with no answer that correctly found nothing went from 13 of 13 to 12 of 13 (the meaning search adds one: "knee replacement surgery", which is near surgical text). Limits: Tamil and Telugu are weaker than Hindi with this small model: a Tamil question usually finds the right references (by their title and summary) but often few or no passages. The next size up (multilingual-e5-base, twice the size) was tried on the same passages and did not tell a real answer from no answer any better, so it is not used. The model cannot reliably say "no answer", so a question counts as answered only when a reference matches by its title and summary (similarity 0.80) or one passage is very close (0.86); passages are then listed down to 0.82, and passages of under 150 characters (a page header, a caption) are not ranked by meaning. Those numbers were set from this small test (see `python evaluate_semantic_search.py --sweep`), so re-run it with your own questions before relying on them. Passages of a PDF attached after the index was built are found by words only until `build_semantic_index.py` is run again (a doctor's own references are matched on the spot). The model needs about 300 MB of memory, so it is not in the Docker image and is off on the free Render plan, where the search works by words as before.

**Code set data.** ICD-10 codes in `backend/app/data/icd10_obstetric.json` were checked against the WHO ICD-10 (2019) tabular list. The earlier drug-safety list (`drug_safety_labels.json`) was removed along with the drug safety check; on start-up the app also removes any leftover drug-safety lists and blood-pressure or weight rules from an existing database.

Drafting is deterministic and source-based. It does not silently call a remote LLM or automatically translate clinical text. Real-audio language accuracy still needs clinical validation; the automated voice test checks the API contract with a mocked decoder.

WhatsApp messages are a minimal sign-in prompt with no clinical content. Real sending needs a WhatsApp Business account: set `MATERNASYNC_WHATSAPP_PROVIDER=cloud_api` with the token, phone-number id, app secret and webhook verify token below, and point Meta's webhook at `/api/v2/webhooks/whatsapp`. Sending through Meta has been tested here only against a mocked API, so try it with a test number first. Without credentials the app runs in `simulator` mode in demo mode (every status is labelled SIMULATED) or `manual` mode (composer link plus a staff "I sent it" record, delivery unconfirmed). Due in-app reminders are materialized on portal activity; background push is not configured.

SQLite and keyword retrieval are retained. PostgreSQL/pgvector and passage-constrained LLM summaries are optional infrastructure from the PDF, not required dependencies added here.

The checks were shown to fail on bad wording before being relied on. They check wording and structure; they cannot prove the absence of every possible interpretation.
