# MaternaSync

React/TypeScript patient, doctor and caregiver (a relative or friend the woman invites) portals backed by FastAPI and SQLite, with a care assistant that does routine administrative work for the doctor. The care-team portal is switched off at sign-in but kept in the code (see Care-team login below). The roadmap implementation reuses the existing episodes, assignments, consultations, documents, questions, tasks, notifications, journeys and audit logs.

## Run locally (PowerShell)

```powershell
npm.cmd install
python -m venv backend/venv
backend/venv/Scripts/python.exe -m pip install -r backend/requirements.txt
backend/venv/Scripts/python.exe backend/fetch_reference_documents.py
backend/venv/Scripts/python.exe -m uvicorn backend.app.main:app --reload --port 8001
```

`fetch_reference_documents.py` is optional: it downloads the open-licence guideline PDFs for passage search (see Reference Library below). In another terminal, run `npm.cmd run dev`, then open `http://localhost:5173/signin`. Existing installations can retain their virtual environment and database. New tables are additive and created at API startup. Demo seeds are idempotent.

### Care-team login

The care-team login is **switched off** and replaced by the care assistant plus the doctor. Nothing was deleted: every care-team page, route, endpoint and test is still in the code. Signing in as care team (or using an old care-team token) is refused with a plain message by one check, `deps.refuse_sign_in`, and the nurse, coordinator and "other" sign-up roles are hidden and refused. Set `MATERNASYNC_CARE_TEAM_ENABLED=true` and restart to bring it all back; the automatic care-team tasks and notifications for new uploads and questions come back with it.

### Governance and integrations

Starter education modules are seeded in all four languages as drafts. A doctor approves them from Clinical Settings, one at a time or as a batch with an explicit "I reviewed each" confirmation, before the care companion or summaries can use them. The Hindi, Tamil and Telugu wording of the app and of the starter modules should be checked by a native speaker from the clinic before real use. `node tests/i18n-coverage.mjs` fails if any patient-portal string lacks a translation, and `node tests/patient-references.mjs` checks that every References topic is complete in all four languages.

Follow-up flags and the ICD-10 lookup are deterministic lookups into lists a doctor approved. Follow-up flags only concern check-ins and tasks. The ICD-10 lookup answers what the doctor types and does not read the note; the doctor ticks any code. None of this is a clinical score, a diagnosis or treatment advice, and nothing is acted on until a doctor decides. Clinical resources start as **DRAFT**; approval records the acting doctor and requires a future review date. This is a single-clinic prototype governance workflow, not a claim of institutional or regulatory approval.

**Reference Library.** Real documents only. The earlier demonstration guidelines and the one-link-per-publisher placeholders are removed at startup (an approved placeholder is retired, not deleted, so its history stays in the audit log). The entries live in `backend/app/data/reference_library_*.json` and are loaded idempotently. It is a personal, unversioned shelf: references that came with the app are the same for every doctor and read-only; anything a doctor adds, and every private note, is visible to that doctor only. Licences differ, so only openly licensed documents (WHO under CC BY-NC-SA 3.0 IGO, and the MoHFW GDM guideline, which allows excerpts with acknowledgement) have their PDFs kept for passage search; ICMR, NICE (outside the UK), SIGN and the societies are link-only. Run `backend/venv/Scripts/python.exe backend/fetch_reference_documents.py` once to download those 15 PDFs from their publishers into `backend/reference_documents/` (ignored by git); the next API start splits them into searchable passages. A few entries say in their edition note that they may have been superseded, and figo.org blocks automated checks, so check the current edition before relying on one. A doctor's own PDFs (up to 25 MB, 400 pages) are searched too. The lists that other parts of the app read from (follow-up rules, ICD-10 code sets, patient education, care pathways and note layouts) live under **Clinical Settings**, where each still needs a doctor's approval.

**Code set data.** ICD-10 codes in `backend/app/data/icd10_obstetric.json` were checked against the WHO ICD-10 (2019) tabular list. The earlier drug-safety list (`drug_safety_labels.json`) was removed along with the drug safety check; on start-up the app also removes any leftover drug-safety lists and blood-pressure or weight rules from an existing database.

Drafting is deterministic and source-based. It does not silently call a remote LLM or automatically translate clinical text. Real-audio language accuracy still needs clinical validation; the automated voice test checks the API contract with a mocked decoder.

WhatsApp messages are a minimal sign-in prompt with no clinical content. Real sending needs a WhatsApp Business account: set `MATERNASYNC_WHATSAPP_PROVIDER=cloud_api` with the token, phone-number id, app secret and webhook verify token below, and point Meta's webhook at `/api/v2/webhooks/whatsapp`. Sending through Meta has been tested here only against a mocked API, so try it with a test number first. Without credentials the app runs in `simulator` mode in demo mode (every status is labelled SIMULATED) or `manual` mode (composer link plus a staff "I sent it" record, delivery unconfirmed). Due in-app reminders are materialized on portal activity; background push is not configured.

SQLite and keyword retrieval are retained. PostgreSQL/pgvector and passage-constrained LLM summaries are optional infrastructure from the PDF, not required dependencies added here.

## Validation

```powershell
npm.cmd run build
npm.cmd run lint
node tests/i18n-coverage.mjs
node tests/scope-guard.mjs
backend/venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
backend/venv/Scripts/python.exe -m unittest discover -s backend/tests -v
```

**Scope guard (no interpretation of medical data).** `node tests/scope-guard.mjs` fails if any English text on a translated screen or in a dictionary labels a value ("abnormal", "normal"), compares it with a range, grades a risk ("high risk") or draws a conclusion ("suggests", "diagnosis"); sentences that say the app does *not* do these things, and a short list of reference-category labels, are allowed with a stated reason (`--list` prints them). `backend/tests/test_scope_guard.py` does the same for the server's fixed wording, checks that the lab explainer's wording is identical for a very low, a mid and a very high value (and for positive, negative and reactive results) in all four languages, that a patient explanation only contains the topics the doctor chose, that the code lookup takes a query and not a note, and that the Claude option's answer schemas contain no free-text field. The checks were shown to fail on bad wording before being relied on. They check wording and structure; they cannot prove the absence of every possible interpretation.

`backend/tests/testenv.py` gives all test modules one temporary database with the care-team login switched on (the older tests cover it); `test_assistant_caregiver.py` covers the care-team switch, the caregiver login and its permissions, the care assistant's workflows, policy engine, kill switch and the model step with a stand-in client. Integration tests use a temporary database/upload directory. Coverage includes authentication, role isolation, corrections, rules/versioning, citations, approval, required fields, education visibility, pathways, task assignment, reminders, consent revocation, appointments, outcome denominators, codes/prescriptions, PDF extraction and existing consultation/question/handover flows.

`tests/browser-smoke.mjs` checks all three demo buttons, persistence, consent, Tamil navigation, appointment triage, document release, references, runtime errors and mobile layout. Use an installed Playwright package or set `PLAYWRIGHT_MODULE` to an existing Playwright `index.mjs`.
